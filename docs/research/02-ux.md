## Scope

Research brief #2: personas, the complete reading journey, five core flows, AI-specific news interfaces, and design-system choices for a solo developer building a general-news analysis web app. Korean and global markets remain separate alternatives. This is research and proposed interaction design, not approval of a product roadmap.

**As-of date: 2026-09-15.** Dated empirical findings retain their original observation/publication dates. Undated living documentation and product capabilities below mean **verified on 2026-09-15**, not independently tested in every region or account. Product pages establish documented patterns, not accuracy or conversion performance. Proposed designs, persona details, defaults and success measures are explicitly hypotheses; their citations indicate rationale, not proof that these designs work.

**Evidence limits.** Reuters DNR 2026 was fielded primarily in January–February 2026, with selected March repolls. Its online, quota-based, weighted survey measures self-reports; it underrepresents some offline populations, and several markets have restricted samples. Cross-market averages are not a population-weighted estimate of all humanity. Small changes of about two percentage points warrant caution.[1] No first-party funnel analytics for this proposed app exist in this brief; news avoidance, disabled alerts and declining direct access are adjacent signals, not measured onboarding abandonment.

### 3. Five core user flows

**Proposed on 2026-09-15.** These flows adapt documented cluster/follow/source-navigation patterns and evidence about user control and uncertainty. They are design specifications to validate, not descriptions of an existing app.[5][7][8][10][11][12]

#### Flow 1 — First-run onboarding

```text
Search/shared link/home
  → Read the requested story or sample briefing as a guest
  → Optional “Personalise”
      → Confirm reading language + news edition separately
      → Pick topics [Skip is equally visible]
      → Preview briefing → Save locally
  → Save across devices? → Sign in → Return to the exact story/scroll position
                        ↘ Later → Continue as guest
  → Notification settings offered only after an explicit follow action
```

Proposed recovery: unavailable edition → explain coverage and offer another edition without silently changing language; failed sign-in → retain guest reading and chosen topics. Language selection must not infer political views. Keep the one-sentence AI disclosure next to the example and provide a methods link for depth.[7][11][12]

#### Flow 2 — Daily briefing

```text
Home / chosen digest entry
  → Today [edition + language + “updated at”]
  → Finite list of event clusters
      → Card: headline + concise takeaway + sources + new/developing state
      → Read summary → [Sources / Deep dive / Save / Less of this]
      → Mark read → Next distinct event
  → “You are caught up for this briefing”
      → Optional followed-topic updates / Leave
```

Proposed recovery: no new events → preserve the prior briefing with its date; ingestion delay → state the last successful update; missing AI summary → show source headlines and links. Do not disguise an old briefing as current. The finite end is an overload hypothesis; “Less of this” changes personalisation while an edition-wide view remains accessible.[2][7][12]

#### Flow 3 — Story deep-dive: cluster → sources → timeline

```text
Cluster card / direct link
  → Story overview [event identity + summary version + last update]
  → Key claims [citation beside each] + “Unresolved / disputed” section
  → Select claim → Source passage with publisher, date, original link
  → Compare sources [original reporting / primary document / other coverage]
  → Timeline [event time distinct from publication time]
      → Select event → Supporting sources + changes since previous update
  → Return to summary / Follow / Share this dated version
```

Proposed recovery: mismatched article → report cluster error; unavailable source → keep bibliographic metadata and mark unavailable; uncertain event time → show “time not established,” not a guessed chronology. Give one-source coverage an explicit state. A retracted/corrected claim remains visible in the history with its replacement and reason; do not silently rewrite a shared version.[8][10][12][15]

#### Flow 4 — Follow a topic or entity

```text
Topic/entity link or Search
  → Disambiguation [name + entity type + country/context]
  → Topic/entity page → Follow
  → Immediately appears in Following [no push permission needed]
  → Optional alerts: Off / Digest / Material changes
      → Choose cadence, timezone, quiet hours
      → Explicit enable → Browser permission / channel setup
          → Granted → Show confirmation and sample alert
          → Denied/unavailable → Keep Following + offer in-app updates
  → New relevant event → Deduplicate → Deliver chosen channel
  → Open → Show what changed → Pause / Unfollow / Adjust cadence
```

Proposed recovery: two people share a name → require disambiguation before following; an entity merge → preserve follow intent and explain the redirect. “Material change” needs an editorial definition and evaluation, not just a new article count. Off/digest defaults are an experiment, not a demonstrated optimum for Korean users.[5][8]

#### Flow 5 — Search

```text
Visible Search entry
  → Query [support Korean IME; submit after composition completes]
  → Suggested topics/entities [keyboard accessible; plain submit always works]
  → Results: Stories / Topics & entities / Sources
      → Filters: date range, edition, source language; explicit sort
      → Story result → Deep-dive flow
      → Entity result → Follow flow
      → Optional “Explain these results” → cited answer over selected results
  → Back → Preserve query, filters and scroll
```

Proposed recovery: no results → show active filters, clear/broaden controls and spelling/alias suggestions; uncertain entity → ask which one; answer unsupported by results → return a scoped “not enough evidence” message and usable results. Preserve the original query when offering a translation. Search should remain useful when generation is unavailable.[7][12][20][24]

#### Responsible bias, confidence and provenance

1. **Separate three questions.** Political orientation concerns viewpoint; source reliability concerns a publisher's practices; claim support concerns whether specific evidence supports this sentence. Ground's outlet-level political categories and Liu et al.'s claim-level citation evaluation are different measurements. Proposed UI: separate fields and methods, never a combined “truth score.”[9][15]
2. **Make the rating contestable.** Spinde et al.'s December 2024 preprint reports two experiments (470 and 846 participants) in which training with marked phrases improved subsequent bias detection; it does not validate a universal automated outlet-rating system or transfer to Korean readers. Proposed UI: optional phrase highlights, visible rationale, human/AI authorship, correction/report control and “not assessed.”[13]
3. **Avoid implied endorsement.** Pennycook et al. (2020) found that warning some false headlines could make unmarked headlines seem more accurate. This evidence concerns truth warnings, not political-label bars, so its application here is precautionary inference. Use explicit assessment states; absence of a warning must not mean “verified.”[14]
4. **Do not import US categories into Korea.** Ground declares its US political frame. Proposed Korean launch: show publisher, country, original language, evidence and observable coverage differences first; withhold Korean ideological scores until an owner-approved local methodology, review process and usability evaluation exist. Global editions also need jurisdiction-specific definitions.[9]
5. **Show actionable uncertainty.** PAIR cautions that percentages may be hard to interpret and recommends explaining missing-data failures. Proposed summary header: “AI summary · based on 4 linked reports · updated [time]”; claim badges explain actual support limitations. A model-generated “92% confident” is not a measured probability of truth. Expose numerical scores only after defining and validating the calibration task, separately for language and changing-news conditions.[11][12]
6. **Regulatory direction is transparency, not a mandated ideology gauge.** The European Commission's DSA explanations describe recommender transparency and lighter requirements for small businesses; this does not settle whether this particular app is an online platform within scope. Its July 2026 AI transparency guidance says Article 50 obligations apply from 2026-08-02. Proposed UX: identify AI involvement and disclose actual recommendation inputs; determine applicable duties and exceptions after launch geography and editorial responsibility are chosen. Neither cited guidance is evidence that a red/blue bias scale is required or scientifically valid.[16][31][32]

Copied code still needs maintenance. |
| **shadcn/ui + Radix** | Supported alternative; Radix documents ARIA, focus and keyboard behaviour.[17][21] | Sensible if established in the project or familiar to the developer. Avoid migration whose only rationale is the changed default. |

Tailwind v4's documented browser baseline is Chrome 111, Safari 16.4 and Firefox 128. As of the access date, this is a compatibility constraint, not evidence of the actual installed browsers in the launch audience. Verify older devices and Korean in-app webviews before committing to that support floor.[19]

#### Mobile-first, with a real desktop reading mode

Historical device evidence: DNR **2025-06-17** describes younger groups as smartphone-first for their first morning news encounter, while over-55s rely more on TV/radio/print; Portugal and Japan remain TV-first overall. This does not provide a verified 2026 smartphone-versus-desktop percentage.[6] DNR 2026's platform shift supports shareable entry points but must not be reinterpreted as device market share.[2]

**Proposal:** prioritise a responsive mobile story page and finite briefing; on wide screens add a stable evidence pane beside the same reading column. Keep sources/timeline equally reachable on small screens through labelled sections, not cramped multi-column charts. A native app, autoplay video feed and a desktop-only analyst dashboard are separate investments to validate. Korean portal habits warrant testing actual portal/in-app-browser entry; global research must select countries and devices instead of assuming one worldwide pattern.[3][6][10]

#### Accessibility and dark mode

**Target: WCAG 2.2 AA, checked against the current Recommendation on 2026-09-15.** An accessible library does not certify the completed application; content, labels, composition and styling remain the developer's responsibility.[20][21][24]

| Requirement | Concrete implication for this app |
|---|---|
| Contrast: 4.5:1 ordinary text, 3:1 qualifying large text; relevant non-text UI contrast 3:1; no colour-only meaning.[24][33][34] | Source-spectrum segments need text/counts; uncertainty and correction states need words/icons as well as colours. Check summary links, muted dates and highlights in both themes. |

#### Reading typography, including Korean

W3C's line-height technique discusses 1.5–2 as useful spacing; Korean Layout Requirements allow Hangul line breaking by character **or** word. CSS `keep-all` changes CJK breaking behaviour. There is no universal standards requirement to set every Korean paragraph to `keep-all`.[27][28][29] Pretendard's first-party repository provides a variable font, subsetting options and SIL Open Font License information.[30] These living references were checked **2026-09-15**.

| Setting | Proposed starting point, to validate on actual content |
|---|---|
| Body font | One Korean/Latin-capable family such as Pretendard; system fallback including Apple SD Gothic Neo/Malgun Gothic/sans-serif. Avoid multiple large font families before measuring loading and fallback layout.[30] |
| Size and line height | Start at 17–18 CSS pixels with user resizing; English around 1.6–1.75, Korean around 1.7–1.8. These are test values, not survey findings or WCAG minimums.[26][27] |
| Measure | Start near 60–72 `ch` for English and roughly 32–40 `em` for Korean, constrained by viewport padding. Latin `ch` measures the zero glyph; do not claim it counts Korean characters. Validate reading comfort rather than treating the proposed ranges as universal.[28][38] |
| Korean breaking | Test `word-break: keep-all; overflow-wrap: anywhere` against normal Hangul breaking on narrow screens; watch long compound names, numbers, URLs and unusually long unspaced text. Avoid blanket `break-all` on mixed-script prose. Make headlines and body independent decisions.[28][29] |
| Mixed languages and evidence | Correct document/passage language tags; distinguish original and translated passages; preserve dates, units and names. Keep citations operable without disrupting sentence reading; avoid fully justified paragraphs that create awkward gaps.[10][24][28] |

## Recommendation

**Build the product around understanding a changing story.** The proposed first portfolio-quality slice is a finite briefing leading to a stable story page with a cited summary, source comparison, timeline, explicit unknowns and follow controls. It addresses distinct explanation and verification needs while keeping the five flows coherent.[4][8][10][15]

1. **Implement one interaction vocabulary.** Use “Story,” “Sources,” “Timeline,” “Following” and “Search” consistently. Start greenfield with shadcn/Base UI/Tailwind v4; retain an existing supported base if one is already established. Create a small owned set of story card, claim citation, source row, timeline event and assessment-state components.[17][19][20]
2. **Make trust inspectable from the first screen.** Show AI involvement, source coverage, update time and an obvious route to originals. Distinguish unavailable evidence, disagreement and an actual correction. The AI/ML portfolio signal should be demonstrated citation support and meaningful abstention, with Korean and English cases; the full-stack signal should include stable links, persisted follows, loading/error states and accessible navigation.[10][12][15][32]
3. **Keep the default reading path short.** Guest access, finite briefing, optional account, explicit follows and restrained alert choices are proposed defaults. Test them; the available surveys do not establish their conversion uplift.[2][5][11]
4. **Defer costly surfaces until the core task works.** Free-form global chat, automatic Korean political ratings, a native app, social comments and video generation are not required to prove this UX. Their exclusion is a prioritisation recommendation, not a claim that the market rejects them.[4][9][13]
5. **Validate the five flows with separate Korean and target-country participants.** Proposed research tasks: enter from a shared link; finish a briefing; trace a disputed claim to its source; follow the intended entity without accidentally enabling alerts; recover from a no-result search. Include mobile, desktop, keyboard and screen-reader use. Record comprehension, task completion, citation interpretation and return intent, together with defects; do not call five completed clicks evidence of trust.[1][14][15][24]

**Proposed release gate:** no unsupported claims presented as established facts in the curated demo set; every factual summary claim has inspectable support or an explicit limitation; all five flows have recovery states; corrected/shared stories remain understandable; core tasks pass manual keyboard, zoom/reflow and both-theme checks. Set quantitative production accuracy/latency targets after choosing launch languages, sources and scope, rather than inventing thresholds in this UX brief.[12][15][24]

## Open questions for the interview

1. Which first market and language pair can the owner recruit real users for: Korea, a named English-language country, or another defined segment?
2. Which persona is the first customer: the time-limited briefing reader or the evidence-comparing follower? What existing behaviour must this product replace?
3. Is the central promise “understand today's news,” “compare coverage,” or “track what changed”? Which remains primary when screen space is limited?
4. How much human editorial review can the owner sustain, and who owns corrections and contested labels?
5. Does the owner want ideological labelling at all? If so, which country's framework, licensed rating source or local review process is acceptable?
6. Is a useful anonymous product acceptable, with accounts only for synchronisation? What personalisation data is the owner willing to collect?
7. What qualifies as a material update, what alert channel is desired first, and who determines exception handling for urgent events?
8. Which browser/device support floor and accessibility commitment can the owner maintain, including older Korean in-app browsers?
9. Will readers inspect original-language sources, need translated evidence, or both? Which parts require human-reviewed Korean writing?
10. Is the first evaluation goal a portfolio demonstration, repeated use by a small recruited group, or a paid service? What evidence will count as success?
