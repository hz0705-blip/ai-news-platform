# 구현 티켓은 Claude 단일 세션의 superpowers 사이클로 구현하고, 리뷰는 민감 여부로만 차등하며, Codex는 리서치와 계획 교차 리뷰만 맡는다

구현 → 테스트 → 리뷰 → 개선을 사람이 경계마다 큐를 넘기지 않고 한 사이클로 돌리기 위해, `ready-for-agent`가 붙은 구현 티켓(UI 화면 티켓 포함)은 Claude Code가 obra/superpowers의 writing-plans → subagent-driven-development → finishing-a-development-branch 순서로 맡는다. 계획 전 단계(grill-with-docs → to-spec → to-tickets → triage)와 PR 뒤의 `/code-review`는 기존 스킬을 유지한다. Codex는 `research` 이슈와 Claude가 `codex exec -s read-only`로 넘기는 계획 교차 리뷰만 맡고 저장소를 바꾸지 않는다. superpowers의 유일한 강제 수단은 SessionStart 훅의 `using-superpowers` 주입이며 그 본문이 CLAUDE.md 우선을 명시하므로, 스킬 원문과 다른 규칙은 `CLAUDE.md`에 두고 값은 `docs/agents/project.md`에 둔다.

12개 PR(#14~#25)의 실측으로 사이클을 다음과 같이 고정한다(2026-09-27 개정. 이 ADR은 이전의 0011 서브에이전트 모델 티어, 0012 리뷰 게이트 차등, 0013 UI 티켓 통합을 흡수했다. 원문은 git 이력).

1. **워크트리를 쓰지 않는다.** 동시 구현이 없으므로 메인 체크아웃의 `ticket/<이슈>-<slug>` 브랜치로 충분하다. 워크트리는 `.env` 복사, `node_modules` 재설치, 도구 가드 우회, 문서 편집 시 체크아웃 전환을 매 티켓에 얹었다.
2. **분류는 민감 여부 하나.** 마이그레이션·시크릿·인증·백업·복구를 건드리면 민감: 구현자·리뷰어 fable, 태스크마다 리뷰, 최종 리뷰 + 재검토, 계획 교차 리뷰. 그 밖은 구현자 opus, `/code-review`만. 티켓 등급 셋(경량·표준·민감)과 모델 티어 셋(light·standard·heavy)의 두 분류를 계획마다 적던 것을 합쳤다. 열 사이클에서 태스크 리뷰가 잡은 유효 결함은 민감 태스크(#22 뒷받침 원점 계산)에서만 나왔고 나머지는 `/code-review`가 같은 것을 다시 잡았다.
3. **태스크가 하나면 SDD를 생략한다.** 구현 서브에이전트 하나가 계획을 브리프로 받아 끝까지 구현한다. 브리프 추출·원장·이관 절차가 작은 티켓(#19 255줄, #25 1,073줄: 수정 회차 0, Critical 0)에서는 순수 오버헤드였다.
4. **계획은 인터페이스·테스트 이름·파일 목록·Ruling만.** 태스크 4개 이하, 300줄 이하. 넘으면 티켓을 나눈다. 코드가 든 계획(#23 1,300줄)은 교차 리뷰 지적의 절반 이상이 계획 코드 자체의 오류였다.
5. **문서를 바꾸는 Ruling은 같은 PR에 넣는다.** 머지 승인이 문서 편집 승인을 겸한다. 머지 뒤 별도 반영 커밋(#22까지 5건)이 `/code-review`의 스펙 충돌 오탐을 만들었다.
6. **UI 티켓도 같은 사이클.** ui-skills 원문은 `docs/ui-skills/`에 커밋돼 있어 어느 구현자든 읽는다. Codex 분기(#20, #25)는 pane·수동 승인·브리프 이관·Ruling 왕복을 사람과 컨트롤러 양쪽에 얹었고 시각 품질 이점은 실측되지 않았다.
7. **플러그인 버전 게이트를 두지 않는다.** 마켓플레이스 자동 갱신을 껐으므로 사이클마다 SHA를 대조할 이유가 없다.

## 고려한 대안

- **역할 분담(Claude 계획·리뷰, Codex 구현)**: 경계마다 사람이 두 도구 사이 큐를 넘겨야 한다.
- **superpowers 원문 그대로**: brainstorming이 스펙과 별도의 설계 문서를 만들고, park·complete가 미해결 Critical을 안고 넘어가며, 워크트리를 강제한다.
- **티켓당 구현자 하나로 SDD 전면 폐지**: 절차는 가장 단순하나 큰 티켓(#22 9태스크 3,566줄)을 한 컨텍스트로 받게 되고, 티켓 분할이 사용자 전용 스킬에 걸려 부담이 사용자에게 간다. 크기로 가르는 3번을 택했다.
- **다섯 겹 리뷰 유지**: 같은 모델 계열의 한계를 겹수로 보완한다는 논리였으나 실측에서 비민감 티켓의 태스크·최종 리뷰는 `/code-review`와 중복이었다.

## 결과

- 사람의 판단 지점은 `ready-for-agent` 부착과 머지 승인 둘이다. 증거 경로는 티켓 → 계획 파일(미추적) → PR 본문 "무엇을 남겼나" → `/code-review` 코멘트.
- 비민감 티켓은 `/code-review`가 유일한 브랜치 리뷰다. Critical/Important가 나오면 수정 1회 + 재검토 1회 뒤 blocked.
- 재검토 조건: 비민감 티켓에서 `/code-review`가 Critical을 두 번 잡으면 태스크 리뷰를 되살린다. 300줄 상한이 티켓 분할을 지나치게 늘리면(사이클당 3개 이상) 상한을 올린다. Claude 구현 `ui` 티켓 두 건에서 시각·접근성 Important가 Codex 실측(3건)보다 많으면 스킬 선택 절차를 강화한다.
- 절차가 다시 바뀌면 새 ADR 대신 이 ADR과 `CLAUDE.md`를 고친다.
