# 리뷰 게이트는 티켓 등급으로 차등하고, 계획은 인터페이스만 적으며, 문서를 바꾸는 Ruling은 같은 PR에 넣는다

ADR-0007의 사이클은 티켓 크기와 무관하게 리뷰를 다섯 겹(계획 Codex 교차 리뷰, 태스크마다 리뷰어, 최종 리뷰, `/code-review` 두 축, 머지 승인) 돌렸다. #14~#23 열 사이클의 결과는 대부분 Minor뿐이었고(#19: 3파일 255줄, 수정 회차 0, Critical·Important 0), 계획 파일은 구현 코드를 전부 담아 1,300줄(#23)까지 커졌으며, 스펙 의미를 바꾸는 Ruling은 PR 본문에만 남았다가 머지 뒤 별도 `docs(repo)` 커밋 5건으로 늦게 반영돼 `/code-review`가 스펙과 Ruling의 충돌을 잡는 일이 생겼다(#22). 이 ADR은 셋을 바꾼다.

1. **티켓 등급 셋(경량·표준·민감)** 을 계획 시점에 정하고 등급이 리뷰 횟수를 정한다. 경량은 `/code-review`만, 표준은 heavy 태스크 리뷰 + 최종 리뷰 1회 + `/code-review`, 민감(마이그레이션·시크릿·인증·백업·복구)은 종전 그대로. 표는 `docs/agents/project.md` "리뷰 게이트".
2. **계획 파일은 인터페이스·테스트 이름과 단언 요지·파일 목록·Ruling만** 적고 구현 코드 본문은 넣지 않는다. 태스크 4개 이하, 300줄 이하. 넘으면 티켓을 나눈다. PR 크기 규칙(패키지당 400줄)은 지켜진 적이 없어 지우고 티켓 크기 규칙으로 옮긴다.
3. **스펙·ADR·`project.md`의 의미를 바꾸는 Ruling은 같은 PR에 문서 변경 커밋으로** 넣고, 머지 승인이 문서 편집 승인을 겸한다. 머지 뒤 별도 반영 커밋은 만들지 않는다.
4. **리뷰 Minor는 같은 PR에서 고치거나 버린다.** 이슈로 남기는 것은 동작이 바뀌는 것뿐이다.

## 고려한 대안

- **다섯 겹 유지**: 구현자와 리뷰어가 같은 모델 계열이라는 한계를 겹수로 보완한다는 ADR-0007의 논리. 그러나 열 사이클의 실측에서 태스크 리뷰가 잡은 유효 결함은 heavy 태스크(#22 Task 4 뒷받침 원점 계산)에서만 나왔고, 나머지는 `/code-review`가 같은 것을 다시 잡았다.
- **`/code-review`를 없애고 최종 리뷰만**: `/code-review`는 스펙 대조 축이 있어 Ruling과 스펙의 충돌을 잡는 유일한 게이트다. 남긴다.
- **계획에 코드 유지**: superpowers writing-plans 원문의 방식. 구현자가 opus 이상이면 계획의 코드를 그대로 옮기는 일보다 인터페이스에서 구현하는 편이 정확했고, 코드가 든 계획은 교차 리뷰 지적(14~19건)의 절반 이상이 계획 코드 자체의 오류였다.

## 결과

- 사이클당 서브에이전트 호출이 표준 티켓에서 대략 절반으로 준다(태스크 리뷰 N회 → heavy만, 교차 리뷰는 태스크 4개일 때만).
- 최종 리뷰가 없는 경량 티켓은 `/code-review`가 유일한 브랜치 전체 리뷰다. Critical/Important가 나오면 blocked 규칙을 그대로 적용한다.
- 필수 승인은 셋(머지·main 직접 push·PR 밖의 지속 문서 편집)으로 유지하되 PR 안 문서 변경은 머지 승인에 흡수된다.
- 재검토 조건: 경량·표준 티켓에서 `/code-review`가 Critical을 잡는 일이 두 번 생기면 표준의 태스크 리뷰를 되살린다. 계획 300줄 상한이 티켓 분할을 지나치게 늘리면(사이클당 티켓 3개 이상) 상한을 올린다.
